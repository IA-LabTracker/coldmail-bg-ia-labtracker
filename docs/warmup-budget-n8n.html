Integração Warm-up Budget

Consulta ao orçamento diário de warm-up antes de cada disparo por caixa de envio.

Visão geral

A plataforma gerencia o ritmo de aquecimento (warm-up) de cada caixa de envio: volume inicial, incremento diário, meta diária, dias úteis, pausa automática por bounce. Todo esse estado fica em sender_warmups no Supabase.

Pra o N8N não precisar replicar essa lógica, foi criada uma edge function que expõe, pra um sender_email_id, quantos emails podem ser enviados hoje e quantos já foram. O N8N faz uma chamada HTTP antes de cada disparo e decide: manda ou pula.

Endpoint

Método
GET
URL
https://kxgwviiewmnmignqmptu.supabase.co/functions/v1/warmup-budget

Exemplo de chamada

# bash / curl
curl "https://kxgwviiewmnmignqmptu.supabase.co/functions/v1/warmup-budget?sender_email_id=ee9ee28f-97a6-43a6-beb9-c5daca42f6f9" \
  -H "Authorization: Bearer <ANON_KEY>"

Resposta

Sempre retorna JSON com HTTP 200, mesmo quando a caixa está pausada ou sem warmup configurado. Erros são indicados via status, não via código HTTP.

CampoTipoDescrição
enabled boolean Warm-up está ativo? Se false, não dispara.
status string Estado atual: active, rest_day, paused, auto_paused, ou no_warmup_configured.
sender_email string Email do sender (lowercase).
current_day integer Dia da rampa (1-based, contando só dias úteis se configurado).
daily_limit integer Meta diária (topo da rampa).
allowed_today integer Quantos emails de warm-up podem ser enviados hoje no total.
already_sent integer Quantos já saíram hoje (consulta email_warmup_interactions).
remaining integer Quantos ainda faltam hoje — é esse campo que define se dispara.
is_rest_day boolean Hoje é fim de semana e business_days_only = true.
is_at_target boolean A rampa já chegou no topo (allowed_today === daily_limit).
paused_reason string/null Motivo da pausa automática (ex: "Bounce 7% > 5%"). Null se não pausou.

Fluxo no N8N

Pra cada caixa que o fluxo vai disparar warm-up, execute:

  1. HTTP Request → GET no endpoint acima, passando o sender_email_id da caixa atual na query string.
  2. IF node com a condição $json.remaining > 0.
  3. TRUE → segue pro disparo do email (cria a interação, manda, grava em email_warmup_interactions com interaction_type = 'sent').
  4. FALSE → pula essa caixa nessa rodada (não precisa tratar diferente os sub-estados paused, rest_day, etc. — todos retornam remaining: 0).
Importante
O N8N não precisa saber fazer cálculo de rampa, nem consultar Supabase diretamente. Só olha pro campo remaining e decide. Toda a lógica de dias úteis, rampa, auto-pausa, etc. fica no backend.

Tabela de estados — ação no N8N

StatusSignificadoAção
active Warm-up rodando normalmente Se remaining > 0, dispara. Senão skip.
rest_day Fim de semana (se business_days_only) Skip. Retomar segunda-feira.
paused Usuário pausou no dashboard Skip.
auto_paused Bounce rate estourou o limite Skip. Usuário vai reativar manualmente depois de investigar.
no_warmup_configured Sender sem registro de warm-up Skip. Provável que a caixa nem deveria estar no fluxo.

Rate limiting

A edge function tem overhead baixo (2 queries ao Postgres), mas vale lembrar que a API do Supabase tem limites. Pra um batch de ~100 caixas, uma chamada por caixa é seguro. Se escalar muito, podemos expor um endpoint batch que recebe um array de IDs e retorna todos de uma vez — só pedir.

Observações

  • O cálculo de "hoje" usa o timezone do servidor (UTC). Na prática, envios feitos de 21h do Brasil em diante contam no "dia seguinte" no banco. Impacto mínimo mas vale ter ciência.
  • A função já é idempotente — chamar várias vezes retorna o mesmo resultado (só lê, nunca escreve).
  • Se aparecer algum status novo no futuro (ex: cooldown pós-auto-pausa), vamos manter remaining = 0 pros status restritivos — ou seja, o critério remaining > 0 continua sendo suficiente no N8N.
